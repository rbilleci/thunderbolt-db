## Correctness — fix BEFORE wiring `WaveReadEngine` into any query path

### C1 — Occupancy trap: `threads` is unvalidated (HIGH)
`new()` launches `blocks = threads.div_ceil(256)` (`wave.rs:437`) with **no occupancy check**. Grid-stride
correctness *requires every launched thread to be simultaneously resident*: index `i` is owned by exactly
thread `i mod T` (`T` = total launched threads, computed at runtime, `wave.rs:192`). In a **persistent**
kernel, resident blocks never exit, so any block that does not fit at launch is **never scheduled**, and the
indices it owns are **never drained** → `completed` never reaches `head` → `harvest` hangs until the ~30s
`%globaltimer` backstop → the wave returns empty/wrong rows.

- The current tests never trip it (≤8192 threads = 32 blocks ≪ 188 SMs), so it is latent.
- The docs frame this only as "*thread 0* liveness" (`wave.rs:659`). It is stronger: **every** thread/block
  must be co-resident, not just thread 0. Sharpen the doc and, more importantly, enforce it.
- **Fix:** at construction, query `cuOccupancyMaxActiveBlocksPerMultiprocessor(kernel, 256)` × SM count and
  require `blocks ≤` that (else error loudly, or clamp `threads` to a safe ceiling). This is the persistent-
  kernel occupancy invariant; it must be enforced, not assumed — a violation is a silent 30s stall + wrong
  result, which is the worst failure class for the read path.

### C2 — u32 cumulative-counter wrap (MED — their own TODO; elevate it)
`head` / `completed` / `base` are cumulative u32 (`wave.rs:675-677`). After ~4.3B lookups (reachable in
hours–days on a busy server) they wrap. At wrap the mandatory `completed < base` guard (`wave.rs:677`)
false-fires — `completed` has wrapped to a small value while `base` is still large — so `harvest` returns
`None` forever → hang. Widen the counters (and the `WaveTicket`/mirror) to **u64** before production wiring.
Cheap change, real production hang.

### C3 — silent `status==0` skip (minor, defense-in-depth)
`read_records` silently `continue`s on `status==0` (`wave.rs:725`, comment "0 would be a bug"). If the gate
ever admits an unwritten slot (a C1 violation, or a future pipelining change — see P2), those records are
dropped rather than surfaced. Add `debug_assert!(status != 0, ...)` so a gate violation fails loudly in
tests instead of returning short/silent results.

## Performance — two levers

### P1 — needles-to-device — ❌ TESTED + REJECTED (2026-06-28; hypothesis wrong)
**UPDATE:** the implementor tried this and the reviewer concurs with rejecting it — it does NOT help (see
DECISIONS "R2.2 P1 needles-to-device = TRIED + REJECTED"). Moving needles to a device ring left large-batch
throughput unchanged (30.7M vs 31.3M = noise; the ~5µs HtoD is nothing vs the ~2.1ms drain) and REGRESSED
every small batch (per-submit HtoD+sync latency: batch1 1.72×→1.46×). The review's symmetry argument with the
record-WRITE ring was wrong: the needle READ is 4 bytes, coalesced, and L2-cacheable (cheap), whereas the
record write is 32 bytes, host-mapped, uncached (the real cap, already fixed). The residual ~31.8M is the
GATHER + 32B record materialization; the bare probe's 45M was a simpler single-u64 kernel and was never an
apples-to-apples target. **~31.8M is the realistic in-crate ceiling for this workload — do not pursue P1.**
The remaining real lever is **P2** (below). Original (now-falsified) hypothesis kept for the record:

The needle ring is **device-mapped pinned** (`wave.rs:347`), so the kernel reads each needle over PCIe
(`ld.volatile.global.u32 [ring]`, `wave.rs:243`). This is the exact mirror of the per-needle record-write
bottleneck already fixed for the result side. Apply the same fix to the **read** side: in `submit_async`,
bulk-`HtoD` the needle batch into a **device** ring (one transfer), and have the kernel read needles from
device memory at full bandwidth. This is the path from ~31.8M toward the bare-probe ~45M the commit cites,
and it is a contained change reusing a pattern that already worked. (If the small-batch HtoD setup latency
hurts, keep a host-mapped path for tiny waves — but device+HtoD is the large-batch win.)

### P2 — per-slot status gate → bounded-depth pipelining → the CONCURRENT regime (HIGH for the premise)
The harvest gate is the cumulative `completed` counter (`wave.rs:677`). This is a contiguous-prefix signal
**only in single-flight** — `head` bounds processing, so `completed == base+len` implies `[base, base+len)`
are all done. With multiple waves in flight, `head` runs ahead, grid-stride threads process indices out of
global order, and `completed ≥ base+len` can be satisfied by a **non-contiguous** set while a slot inside the
wave is still unwritten. The team correctly identified and documented this and restricted to single-flight
(`aeaee74d`).

But single-flight caps the engine at **one wave at a time**, and the wave engine's largest advantage over
launch-per-batch is the **concurrent / many-producer / continuous-fill** regime (many clients, ring kept
full, results drained async) — which needs multiple waves in flight. To unlock it:

- Switch the harvest gate to a **per-slot status** check: each record's `status` byte is already written
  LAST (`wave.rs:300`); make that ordering load-bearing (status released after the body, via the existing
  `membar.sys`), and have `harvest` confirm a wave by reading its slots' statuses rather than the global
  counter. Then the host can keep **depth-K** waves in flight (bounded by `ring_capacity`) and harvest each
  independently and in any order.
- This is what enables the **open-loop offered-rate** benchmark that is the real evidence gate (and what the
  original review asked for). The current single-flight win is genuine; the headline regime is still
  unmeasured, and P2 is the unlock.

### P3 — small-batch DtoH latency ~6µs (minor)
For tiny waves the separate-stream `DtoH` + sync setup dominates (~6µs). A host-mapped record-read fast-path
for `len` below a threshold would shave it, but the wave already beats lpb at small batches → low priority.

## Framing note (so the result isn't over-read)

The benchmark is still **single-flight** (`submit → harvest` serialized). It legitimately shows wave > lpb
across the sweep — a real, correct result. But the regime the wave engine exists for (concurrent,
continuous-fill, many producers) is **still not directly benchmarked**; P2 + an offered-rate harness closes
that, and it is where the advantage should be largest. State the current result as "single-flight wave
beats lpb across the sweep," not "the wave engine's premise is proven" — the concurrent premise is the next
gate and depends on P2.

## Recommended sequence

1. ✅ **C1 + C2 + C3** — correctness gates. LANDED (`6b28832e`) before any engine wiring.
2. ~~**P1** — needles-to-device~~ ❌ TESTED + REJECTED (no help; ~31.8M is the realistic ceiling — see P1 above).
3. **P2 + offered-rate harness** — per-slot pipelining, then the concurrent/offered-rate test. With P1 closed
   and C1/C2/C3 landed, **this is the single remaining open lever**, and the one that matters most: it is the
   premise gate (the concurrent regime the wave exists for) and the decision input for whether wave-in-engine
   is worth the wiring vs. R1's launch-per-batch default.

## Acceptance criteria

- **C1:** constructing with `threads` that would exceed resident capacity returns a clear error (or clamps);
  add a test asserting a too-large `threads` does not silently hang.
- **C2:** counters/ticket/mirror are u64; add a wrap-region test (seed `head` near the old u32 boundary).
- **P1:** oracle byte-identical AND the stale-DtoH stress gate (`aeaee74d`) still pass at max threads after
  the needle path moves to device; report the new large-batch throughput.
- **P2:** a depth-K pipelined test keeps K waves in flight, harvests them (in any order), and is
  byte-identical to the R1 index probe under reused-slot rotation; the offered-rate benchmark reports
  saturation throughput + p99 vs offered load for wave and lpb under equal concurrency.

Until C1/C2 land, treat `WaveReadEngine` as not-yet-wireable; until P2 + offered-rate land, treat the
concurrent-regime win as unproven and keep R1's launch-per-batch index probe as the shipped default.
