## TL;DR / verdict

The benchmark's **measurements are correct**, but it tested the wave engine in the **one regime guaranteed to make it lose** (single-client, synchronous, submit-and-block request-response), measured **per-batch round-trip latency**, and reported it as **throughput**. It then generalized that to *"the wave engine loses / R2's premise does not hold / PARK."*

That generalization is **not supported by the evidence presented.** What was actually shown is narrower and unsurprising: *a **blocking** wave engine loses in synchronous single-thread mode.* The regime the wave engine exists for — **sustained continuous fill, many requests in flight, async completion, under concurrency** — was **never tested.** The probes already hit ~45M req/s in exactly that regime.

**Decision triage:**
- ✅ KEEP: "do not drop a *blocking* wave engine into the *current request-response* engine path." That is correct.
- ✅ KEEP: all R2.1/R2.2 building blocks, the `cuMemAlloc` freeze root-cause, the SM-coexistence result, the `all_done` audit, and the "measure first" discipline. Good work, all valid.
- ❌ FIX: the headline/conclusion ("wave LOSES", "premise does not hold", "PARK"). It overreaches and risks a future agent abandoning a direction that was never run in its target regime.

**Bottom line: deferring the wave engine is reasonable; concluding it is beaten is not shown. Re-frame, then run the correct test before any final call.**

## What the benchmark actually measured (the core flaw)

`WaveReadEngine::submit` (`wave.rs:489`, doc at `:254` "runs one wave at a time (serialized)") is **synchronous and blocking**: it publishes the head, then spin-polls `cuMemcpyDtoH` on the `completed` counter until the wave fully drains, *then* returns. The benchmark loop is:

```rust
for it in 0..iters { engine.submit(&needles_for(batch, it)); }   // each call BLOCKS to completion
```

So every batch pays a full host→device→host round-trip with **zero overlap**: the kernel idles waiting for the next head; the host idles polling the counter. This measures **per-batch round-trip latency**, and the reported "lookups/s" is just `batch_size / latency`. It is a **latency test mislabeled as a throughput test.**

**The numbers are the tell.** Wave throughput is essentially **flat** while launch-per-batch (lpb) **scales**:

| batch | wave | lpb | wave/lpb |
|---|---|---|---|
| 1 | 8.6k | 39k | 0.22× |
| 8 | 35k | 309k | 0.11× |
| 64 | 55k | 2.29M | 0.02× |
| 256 | 60k | 7.08M | 0.01× |

A real throughput engine's numbers **rise** with offered concurrency. Flat-at-~1/latency (8.6k→60k) is the signature of measuring the reciprocal of round-trip latency. Per-submit even **worsens** (116µs→4.3ms) because larger serialized waves drain slower under polling congestion — the opposite of the amortization batching is supposed to buy. The commit message itself states the cause: *"The probes' ~45M req/s was ONE GIANT continuous-fill wave (round-trip amortized over 200k requests); request-response does not amortize it."* That is precisely the point — the benchmark removed the amortization.

---

## Secondary issues (each widens the gap unfairly)

1. **Completion-mechanism asymmetry.** Wave completes via **busy `cuMemcpyDtoH` polling** while **1024 kernel threads also poll host-mapped memory over PCIe** — both directions congest the bus. lpb completes via a **driver-optimized stream-sync**. Much of the gap is poll-vs-sync, an implementation artifact, not a property of the wave model.
2. **"Continuous fill" conflated with batch size.** The comment at `wave.rs:742` ("large single waves = continuous fill") is the misconception: one bigger *blocking* submit is not continuous fill. Continuous fill is **many waves in flight at once**, which the benchmark never creates.
3. **No concurrency.** Single host thread, synchronous. Real OLTP load is many connections; the coalescer aggregating concurrent requests is exactly what would keep a ring full. Not modeled.
4. **The implementation is blocking by construction.** R2.1/R2.2 built a *request-response* wave engine (`submit` blocks). It therefore added persistent-kernel cost **without** the pipelining that pays for it. The benchmark faithfully measured *that* engine losing — but that engine is not the continuous-fill engine the probes validated. This is the root issue: the thing built cannot express its own value proposition, so the benchmark could not have shown a win.

## Directive — what to do to fix it (in priority order)

### A. Re-frame the recorded conclusion (cheap; do first)
Edit DECISIONS ADR-008 "R2.2 EVIDENCE GATE" and HANDOVER. Replace *"persistent wave LOSES to launch-per-batch / R2's premise does NOT hold / PARK"* with the accurate, narrower claim:

> A **blocking (request-response) wave engine** loses to launch-per-batch in **single-client synchronous** point reads (expected — it pays a per-batch round-trip with no overlap and bus-congesting poll completion). The wave engine's actual premise — **continuous-fill throughput under concurrency with async completion** — is **UNTESTED**. Deferring wave-in-engine is justified by cost/risk, **not** by a head-to-head loss in its target regime.

Keep the valid narrow conclusion (don't wire a blocking wave into the current request-response path). Do not present the result as "the wave engine is beaten."

### B. Give `WaveReadEngine` an async / pipelined API (the real implementation gap)
The current blocking `submit` cannot be in flight. Add:
- `submit_async(needles) -> Ticket` — publish head, return immediately (the ticket = the cumulative head value), **do not wait**.
- `harvest(ticket) -> Option<rows>` — non-blocking: check `completed >= ticket` (single DtoH or host-mapped read), read records if ready.
This lets the host keep **depth K** waves in flight and drain asynchronously — the only way the engine can amortize the round-trip.

### C. Fix the completion path so it isn't the bottleneck/artifact
Replace per-batch busy `cuMemcpyDtoH` polling with one of: a CUDA **event**/`cuStreamWaitValue`-style signal, a **host-mapped `completed` read with backoff** (not a tight DtoH loop), or device-side completion notification. At minimum, **isolate and report** the polling-congestion cost separately so it isn't silently folded into "the wave engine is slow." Also sweep `wave_threads` lower — 1024 pollers is a suspect; the data plane likely saturates well below that.

### D. Build the correct benchmark (the actual evidence gate)
This is the test that decides the premise. Two shapes, build whichever is cheaper first:
- **Pipelined depth sweep (simplest):** keep **K** waves in flight via `submit_async`/`harvest` (K ∈ {1,2,4,8,16,…}); measure **steady-state drain throughput** vs K. Premise holds iff throughput **rises with K** and clears the lpb ceiling (~7M execution-layer) at some modest K.
- **Open-loop offered-rate (most faithful — already parked in HANDOVER):** N concurrent producers issue point lookups at a **rising offered rate**; path A = coalesce→launch→sync→respond, path B = feed the ring continuously + async respond; measure **saturation throughput + p99 latency** for both as load climbs.

### E. Preallocate to dodge the `cuMemAlloc` freeze for a real run
The freeze (`a8d29946`) is real but not fundamental: `cuMemAlloc/cuMemFree` device-sync while the persistent kernel is live. Fix by **preallocating all device buffers before launching the kernel** (fixed pool, no alloc on the hot path) or using **`cuMemAllocAsync`** (stream-ordered, no device-sync). Then the wave and lpb paths can be measured **with the kernel live** and even **concurrently**, which the current benchmark could not do (it had to shut the wave down first).

### F. Re-decide on the right evidence
After D, the call is honest either way:
- Wave throughput **rises with concurrency and beats lpb** above some threshold → the wave engine + an async engine model is **justified** (a larger change, now evidence-backed).
- Wave **still loses even in continuous fill** under realistic concurrency → **park with confidence**, and record *that* as the evidence.
- Inconclusive → one more targeted probe, not a verdict.

## Acceptance criteria for the corrected benchmark (so "done right" is unambiguous)

1. **Concurrency is the swept variable** (depth K or offered rate), not just batch size. Throughput must be reported **as a curve vs concurrency**, never a single ratio.
2. **Both paths run under identical concurrency** (lpb via multiple streams / coalesced launches; wave via the ring) — apples to apples.
3. **Completion is not a tight DtoH poll loop** (event/backoff), or its cost is measured and reported separately.
4. **Correctness asserted**: wave rows are **byte-identical** to the lpb/R1 index probe over the same needles (a fast wave that returns wrong/empty rows is not a win) — reuse the existing parity assertion.
5. **The kernel is live during both measurements** (preallocated buffers), so the comparison reflects real coexistence.
6. **Report**: saturation throughput, p50/p99 latency, and the K (or offered rate) at which wave crosses lpb (or a clear statement that it never does, with the ceiling).

Until a benchmark meeting these criteria runs, treat the wave-engine throughput question as **open**, and the R1 launch-per-batch index probe as the **shipped, correct point-read default** (which it is).
