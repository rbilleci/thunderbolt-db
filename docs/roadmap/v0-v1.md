# Implementation Roadmap (v0 -> v1 + P8)

## v0 (Foundation)

- Commit path through `LogReplicator` (`LocalReplicator` implementation)
- CPU reference semantics for core SQL subset
- WAL + recovery + invariant enforcement
- Device-aware planning shape (even if many nodes route to CPU)
- GPU guardrails + parity harness setup

## v0.5 (Replication skeleton)

- `RaftReplicator` scaffolding
- Role-aware write/read gates
- Commit/applied index tracking
- Snapshot metadata/export hooks

## v1 (Operational replication)

- 3-node raft deployment for WAL replication
- Follower apply + catch-up
- Failover basics and readiness gates
- Deterministic replay validation for GPU-eligible paths
- PostgreSQL async/application-driver compatibility gate for the supported SQL/protocol subset:
  `tokio-postgres`, `sqlx`, `asyncpg`, `node-postgres`, `psycopg`, `pgx`, and JDBC/R2DBC
  smoke apps should cover connect/startup, simple query, prepared/bind query,
  empty results, error recovery, pooled reconnect, and explicit unsupported
  feature handling.
- P7 performance proof must distinguish CUDA runtime/probe caching from
  GPU-resident table data. The current residency baseline has resident-byte
  accounting, WAL-safe invalidation metadata, mutation refresh-cost evidence,
  memory-pressure fallback metadata, deterministic resident-snapshot budget
  admission/eviction, a bounded resident table-data snapshot SELECT probe
  with zero per-query H2D transfer for the app lookup workload and supported
  aggregate/distinct SQL shapes, plus a retained real CUDA allocation/copy
  handle and retained-device-memory `COUNT(*)`, int4 equality-predicate
  `COUNT(*)`, int4 membership-predicate `COUNT(*)`, int4 range-predicate `COUNT(*)`,
  int4 `BETWEEN`-predicate `COUNT(*)`, retained int4 `AND`/`OR` filter-group
  `COUNT(*)`, retained text prefix `LIKE` `COUNT(*)`, scalar
  `SUM(int4)`/`AVG(int4)`/`MIN(int4)`/`MAX(int4)`, filtered scalar
  `SUM(int4)`/`AVG(int4)`/`MIN(int4)`/`MAX(int4)` with an int4 comparison predicate,
  `BETWEEN` scalar `SUM(int4)`/`AVG(int4)`/`MIN(int4)`/`MAX(int4)`, int4
  predicate-projection, int4 paginated distinct projection, int4 paginated filtered distinct projection,
  bounded paginated filtered ordered-projection, grouped
  `COUNT(*)`/`SUM(int4)`/`AVG(int4)`/`MIN(int4)`/`MAX(int4)` with grouped
  `HAVING`, and filtered grouped
  `COUNT(*)`/`SUM(int4)`/`AVG(int4)`/`MIN(int4)`/`MAX(int4)` with filtered
  grouped `HAVING` query-kernel proofs over the encoded resident snapshot
  bytes when local driver hardware is available.
  Engine status and telemetry now report
  resident tables, per-GPU bytes/budgets, validity/invalidation state,
  admission/eviction/device-memory proof metadata, and latest resident route
  decisions with resident/cold H2D byte estimates plus conservative D2H byte
  and row estimates plus the latest accepted route execution's observed H2D/D2H,
  kernel-sample, kernel-millisecond, and result-row deltas. An explicit opt-in resident execution path now consumes accepted
  route decisions for retained-device-memory `COUNT(*)`, supported count
  predicates, unfiltered/filtered/`BETWEEN` int4 scalar aggregates, and bounded
  int4 range-predicate projections plus bounded int4 distinct projections and
  bounded unfiltered/filtered int4 grouped aggregate shapes with grouped
  `HAVING`; normal SQL routing now consumes accepted decisions by default for
  the same bounded shapes.
  The supported retained string/filter expression-kernel families are closed for
  the current SQL subset; broad production CUDA cache/allocator claims still
  require richer expressions beyond literal comparison/range/membership/prefix/count/aggregate/projection
  shapes, production cache orchestration beyond the bounded operator-triggered
  warmup and scheduler-friendly maintenance-tick policy, and broader CUDA event
  timing coverage beyond the first accepted-route resident-kernel samples.

## Explicitly out-of-scope until post-v1

- Full cluster reconfiguration automation
- Advanced multi-region failover automation
- Broad extension/plugin surface
- Broad async-driver feature parity beyond the supported subset, including
  binary formats, COPY streaming, richer type metadata/OID behavior, advanced
  portal behavior, TLS/GSS/cancel/notification depth, and broad SQL grammar.

## P8 (GPU-Optimized Storage Engine Design)

P8 is the design track for replacing the bootstrap tuple-store assumption with
a deliberate high-performance storage architecture for the GPU engine. The
design starts in `docs/architecture/10-p8-gpu-optimized-storage-engine.md`.

The target is not to make GPU memory durable. WAL/checkpoint/archive replay
remains the source of truth. P8 should define the physical table layout,
CPU/GPU storage tiers, resident cache manager, mutation invalidation and refresh
flow, persistent/resident index strategy, recovery rebuild sequence, and planner
cost hooks required for hot workloads to execute from GPU-resident data.

The first P8 milestone recorded workload assumptions, benchmark questions, and
the smallest implementation slice that can prove the architecture without
weakening WAL-before-visibility. The 2026-05-20 P8 design closeout in
`docs/architecture/10-p8-gpu-optimized-storage-engine.md` fixed that first
slice as a bounded resident-cache-manager proof over one supported public
`int4`/`text` table. The first P8 code slice now implements
`RelationalResidentCache` for residency snapshots, retained device-memory
handles, deterministic budget admission/eviction, rejection decisions,
WAL/memory-pressure invalidation, refresh metadata, status/telemetry exposure,
and benchmark decision output. The next P8 slice adds a conservative
planner-routing decision contract: supported relational `SELECT` shapes can be
checked against valid resident snapshots, retained device memory, query-shape
support, budget, refresh, and transfer-cost facts, with accept/reject reasons
exposed through status/telemetry. The current P8 slice uses those accepted
decisions to drive `Engine::execute_relational_select_with_resident_route(...)`,
an opt-in resident execution path for the supported retained-kernel shapes.
Normal `Engine::execute_relational_select(...)` now consumes accepted resident
route decisions by default for those bounded retained-kernel shapes, including
filtered and `BETWEEN` int4 scalar aggregates plus unfiltered and filtered int4
grouped aggregate shapes with grouped `HAVING`, plus the existing same-column
int4 filtered ordered-projection proof with `ORDER BY`, `LIMIT`, and optional
`OFFSET`, and falls back to the existing MVCC/CUDA-probe path for every rejected
route.
`Engine::warm_relational_residency_with_policy(...)` now provides bounded,
operator-triggered warmup/policy support for supported public base tables,
including named/all-table selection, optional per-GPU budget application,
invalidated-entry refresh, deterministic admission/eviction, memory-pressure
skips, and route-readiness evidence. The checked `resident_warmup_preflight`
example and `scripts/run_p8_resident_warmup_preflight_smoke.sh` expose the same
proof as a local operator dry-run/apply gate covering refresh, memory-pressure,
oversized-budget, and route-readiness evidence, including D2H byte estimates for
the default readiness route. `Engine::maintain_relational_residency_with_policy(...)`
now packages that warmup/refresh path as a scheduler-friendly maintenance tick
over supported public base tables, summarizing warmed, refreshed,
already-resident, skipped, error, route-ready, and route-blocked outcomes for
operator checks without claiming an autonomous daemon. The remaining P8
milestones are richer retained expressions and production cache orchestration
beyond this bounded warmup/preflight, maintenance-tick, and default-routing
slice, plus broader CUDA event timing coverage beyond the first accepted-route
resident-kernel event samples that are exposed separately from metrics-derived
route execution deltas.
